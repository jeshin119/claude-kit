# 한국어 문서 다시 쓰기 기록 (2026-09-08)

doc-protocols 플러그인과 저장소 README의 한국어를 전부 다시 썼다. 이 문서는 무엇이
어색했는지, 왜 CLAUDE.md를 여러 번 고쳐도 남았는지, 어떻게 고쳤는지를 사례와 함께
남긴다. CLAUDE.md에 옮길 규칙은 맨 끝에 모아 두었다.

## 진단: 규칙을 늘려도 남은 이유

기존 CLAUDE.md 규칙은 문장 단위의 결함(무생물 주어, 비유, 조어, 명사구 종결)을
하나씩 금지한다. 그런데 이번에 읽은 문서의 어색함은 대부분 문장 하나가 아니라 문서
전체의 일관성 문제였다. 규칙이 잡지 못한 축은 넷이다.

1. 격식이 문장 안에서 어긋난다. 종결어미는 보고서체(`~한다`)인데 동사가
   구어(돈다, 먹는다, 깐다, 뜬다, 걸린다)다. 읽는 쪽은 문장마다 격식을 다시 맞춰야
   한다.
2. 한 번에 말할 수 있는 것을 끊어 놓는다. "값만 적는다. 판정하지 않는다."처럼 짧은
   문장을 연달아 놓으면 강조처럼 읽히고, 두 문장의 관계(이유, 조건, 대조)를 읽는
   쪽이 채워야 한다.
3. 제목이 영어 의문문 직역이다. "무엇을 푸는가", "왜 남기는가", "언제 쓰는가"는
   What it solves, Why keep it, When to use의 번역이다. 답이 본문 어디에 있는지
   제목만으로 알 수 없다.
4. 맥락 없이 번호와 조어를 쓴다. "12와 15가 비어 있다"는 항목 번호표를 외운
   사람만 읽을 수 있다. "세우기", "자기 신고", "승급", "사슬"은 이 프레임워크 안에서
   만든 말인데 정의 없이 등장한다.

기존 규칙이 잡은 비유·무생물 주어도 여전히 남아 있었다. README를 쓸 때 CLAUDE.md가
구버전이었기 때문이다. 문서는 규칙이 바뀌어도 자동으로 따라오지 않으므로, 규칙을
고친 뒤에는 그 규칙으로 기존 문서를 한 번 훑어야 한다.

## 고친 방법과 사례

### 1. 어휘의 격식을 종결어미에 맞춘다

| 원문 | 수정 |
|---|---|
| 그마저 서버가 계정에 기능을 열어줘야 돈다 | 그것도 서버가 계정에 기능을 열어 줘야 동작한다 |
| 전역에서만 먹는 키가 있다 | 전역에서만 적용되는 키가 있다 |
| 개인 플러그인을 깐다 | 개인 플러그인을 설치한다 |
| 스킬 목록에는 아무것도 안 뜬다 | 스킬 목록에는 아무것도 나타나지 않는다 |
| 하나라도 걸리면 M에서 L로 올린다 | 하나라도 해당하면 승급한다 |
| 스킬의 세우기 절차를 부른다 | 스킬의 생성 절차를 실행한다 |
| ID 없이 만들어진 것은 잡지 못한다 | ID 없이 만들어진 것은 검출하지 못한다 |
| 나 말고 다른 사람이 손댄다 | 나 말고 다른 사람이 수정한다 |
| 코드를 다시 치는 비용 | 코드를 다시 작성하는 비용 |
| 손으로 편집하면 다음 동기화 때 날아간다 | 손으로 편집하면 다음 동기화 때 지워진다 |
| 사본이 갈라진다 | 사본이 원본과 달라진다 |

기준은 "이 동사를 회의록이나 보고서에 쓸 수 있는가"다. 대화에서는 자연스러운
동사라도 `~한다`체 문장에 들어가면 어긋난다.

### 2. 비유를 사실로 바꾼다

| 원문 | 수정 | 비유가 숨긴 사실 |
|---|---|---|
| 그 코드가 맞다고 확인하는 속도가 프로젝트의 상한이 된다 | 프로젝트의 진행 속도는 코드를 쓰는 속도가 아니라 그 코드가 올바른지 확인하는 속도에 따라 정해진다 | 상한(ceiling)이 무엇의 상한인지 |
| 확인하지 않은 코드는 자산이 아니라 부채다 | 확인하지 않은 코드는 남겨 둘수록 고치는 비용이 커진다 | 부채가 구체적으로 어떤 비용인지 |
| 목적이 바람이 아님을 증명한다 | 성공 기준이 달성됐는지 확인한다 | 바람(wish)의 반대가 무엇인지 |
| 한 칸이라도 비면 목적이 아니라 바람이다 | 한 칸이라도 비면 달성 여부를 판정할 수 없는 문장이 된다 | 왜 목적이 아닌지 |
| 결정층이 잡음으로 차서 중요한 결정이 묻힌다 | 중요하지 않은 결정에 중요한 결정이 묻힌다 | 잡음이 무엇인지 |
| 기능 하나를 입구부터 저장소까지 관통시킨다 | 기능 하나를 입구부터 저장소까지 끝까지 구현한다 | 관통이 어떤 작업인지 |
| 사람이 스펙을 확인했는지가 갈림길이다 | 사람이 스펙을 확인했는지가 기준이다 | 무엇을 가르는 기준인지 |
| 같은 말을 두 번 한 것이다 | 스펙이 맞는지 아무도 확인하지 않은 상태다 | 두 번 말한 것이 왜 문제인지 |
| 범위 방어선 역할을 하는 항목 | 범위를 지키는 역할을 하는 항목 | |

비유를 지우면 문장이 길어진다. 그래도 지운다. 비유는 짧아 보이지만 읽는 쪽이 원래
표현(영어 관용구인 경우가 많다)을 되짚어야 뜻이 통하기 때문이다.

사슬 B 가). 한글 맞춤법은 조사를 앞말에 붙이고, 사용자의 CLAUDE.md 예문도 붙여
쓴다(generateContent를, 사슬 B가). 전부 붙였다. 이것만으로 문장 밀도가 눈에 띄게
달라졌다.

- 도식 JSON과 HTML은 같은 라벨 문자열을 갖고 있어서 양쪽에 같은 치환을 적용했다.
  다시 생성하지 않았다.

## CLAUDE.md에 옮길 규칙 (제안)

아래는 기존 규칙과 겹치지 않는 것만 골랐다. 기존 규칙 다음에 붙이면 된다.

- 어휘의 격식을 종결어미에 맞출 것. `~한다`체 문장에 구어 동사를 쓰지 않는다.
  - 돈다 → 실행된다 / 먹는다 → 적용된다 / 깐다 → 설치한다 / 뜬다 → 표시된다
  - 걸린다 → 검출된다, 해당한다 / 부른다 → 호출한다 / 잡는다 → 검출한다
  - 손대다·건드리다 → 수정하다 / 치다 → 작성하다 / 날아가다 → 지워지다
  - 갈라지다 → 달라지다 / 낡았다 → 최신이 아니다 / 갈아엎다 → 전부 교체하다
- 한 번에 말할 수 있는 것은 한 문장으로 쓸 것. 짧은 문장을 연달아 놓지 않는다.
  두 문장의 관계(이유, 조건, 대조)가 있으면 연결어미로 잇는다.
  - 값만 적는다. 판정하지 않는다. → 값만 적고 판정은 하지 않는다.
- 굵은 글자 뒤에 줄표(—)를 붙여 문장을 이어가지 말 것. 완결된 문장으로 쓰거나
  제목으로 올린다.
  - **승급 신호** — 하나라도 걸리면 → 다음 세 신호 중 하나라도 해당하면 승급한다
- 제목을 의문문으로 쓰지 말 것. 영어 제목(What/Why/When)을 "무엇을 ~하는가"로
  옮기지 않는다.
  - 무엇을 푸는가 → 해결하려는 문제 / 언제 쓰는가 → 사용 시점
- 번호·기호로만 가리키지 말 것. 항목 번호는 이름과 함께 쓰고, 문서 안에서 만든
  이름(층, 사슬, 승급)은 문서마다 첫 등장에서 한 줄로 정의한다.
  - 12와 15가 비어 있다 → 12 구현 현황과 15 검증 기록이 비어 있다
- 코드 표기·숫자·영문 뒤의 조사도 붙여 쓸 것.
  - `charter.md` 를 → `charter.md`를 / 15 의 → 15의 / M 에서 → M에서
- 동사를 명사로 굳혀 용어처럼 쓰지 말 것. 절차 이름은 한자어 명사로 쓴다.
  - 세우기 → 생성 / 자기 신고 → 적는 쪽이 스스로 고르는 값
- 규칙을 고친 뒤에는 그 규칙으로 기존 문서를 한 번 훑을 것. 문서는 규칙이 바뀌어도
  따라오지 않는다.

### 국립국어원 지침과 대조한 결과

지침이 드는 결함은 주어와 서술어의 호응, 지나치게 긴 문장, 여러 뜻으로 읽히는 표현,
조사와 어미의 지나친 생략, 대등하지 않은 것의 접속, 영어 번역투(`~에 의해 ~되다`,
사물이나 추상적 대상이 행위의 주어로 나오는 문장, `~을 통해`, `~에 대한`), 일본어
번역투(`~에 있어서`, `~에 있다`), 명사 나열형 문장, 불필요한 피동 `-되다`, 불필요한
`-고 있다`다.

두 README를 검사한 결과 `~을 통해`, `~에 대해`, `~에 의해`, `~에 있어`, 이중 피동,
`-고 있다` 종결은 한 건도 없었다. 사물 주어 능동문("사슬 B가 잡아낸다")은 1차
수정에서 이미 걷어냈다. 즉 문장 단위의 번역투는 이미 CLAUDE.md 규칙으로 잡히고
있었고, 남은 문제는 다른 축에 있었다.

**문장 길이.** 기사는 문장당 25~45어절의 복합문이 기본이고 짧은 문장은 강조할 때만
드물게 쓴다("그만큼 사람의 개입은 줄고 AI의 자율성은 커진다."). 기술 블로그는
10~15어절 단문과 25~35어절 설명문을 섞는다. 논문 초록은 한 문장이 60어절을 넘기도

합치는 기준은 두 문장 사이에 이유·조건·대조 관계가 있는가다. 관계가 없는 짧은 문장
(문단 첫머리의 주제 문장, "올라가지 않는 것이 더 있다."처럼 목록을 여는 문장)은 기사와
블로그에서도 그대로 쓰므로 남겼다.

**문두 접속사.** 기존 규칙은 "문두의 그래서·하지만"을 구어 연결로 보고 지우게 했다.
그런데 기사("그만큼", "이번 조치는"), 기술 블로그("하지만", "따라서", "대신", "결국",
"그래서", "다만", "그런데"), 국립국어원 지침("문장을 끊고 접속하는 말로 다음 문장을
시작하는 것이 적절하다") 모두 문두 접속사를 정상적으로 쓴다. 문제는 접속사가 아니라
구어 어미(`~거든요`)와 같은 접속사의 반복이었다. writing-rules.md의 해당 행을 "구어
어미 제거"로 바꾸고, 문두 접속사는 문장 관계를 밝히는 데 쓰되 같은 것을 문단마다
반복하지 않는다고 고쳤다. 참고로 2차 검토 직전 두 README의 문두 접속사는 "그래서"
3회뿐이었다. 연결어미로 관계를 처리하고 있어서 접속사가 부족하지는 않았다.

**제목.** 기사·논문·보고서는 명사구 제목만 쓴다. 기술 블로그는 이야기체라 "왜
SSE였나", "어떻게 동작하는가" 같은 의문형 소제목도 쓴다. 의문형 제목이 항상 틀린
것은 아니고 장르에 따라 갈린다. README는 참조 문서이므로 명사구를 유지했다.

**영어 고유명사.** 기사는 첫 등장에 한글 음차와 원어를 병기한다("앤트로픽(Anthropic)",
"클로드 코드(Claude Code)"). 기술 블로그는 원어를 그대로 쓰거나 한글(원어)로
병기한다("아크유닛(ArchUnit)"). README는 기술 블로그 관행대로 원어를 그대로 두었다.
음차를 앞세우면 검색이 안 되는 이름이 되기 때문이다.

**조사 붙여쓰기.** 모든 참고 자료가 영문·숫자 뒤 조사를 붙여 쓴다("ArchUnit은",
"SSE는", "13.6%에"). 1차 수정에서 붙인 것이 규범과 맞다.

**단락 구조.** 기사 단락은 3~4문장이고 첫 문장이 사실, 마지막 문장이 해석이다("~로
읽힌다", "~를 보여주는 대목이다"). 기술 블로그는 문제, 대안 비교, 결정, 검증 순서로
쓴다. README 단락도 첫 문장이 주장이고 뒤가 근거인 구조라 큰 차이가 없었다.

**수치와 출처.** 기사와 블로그는 "13.6%", "6배", "신규 위반 0건"처럼 숫자로 말하고
출처("테크크런치에 따르면")를 붙인다. README에서 경험에 근거한 단정("혼자 하는
프로젝트는 대개 완주가 아니라 중단으로 끝나는데")은 그대로 두었다. 근거를 붙이면
좋지만 이 문서에 실측값이 없어서 지어내지 않았다.

### CLAUDE.md에 옮길 규칙 (2차 추가)

- 문장 길이의 기준을 둘 것. 한국어 설명문은 문장당 10~35어절이 보통이다. 6어절
  이하 문장이 연달아 나오면 앞뒤 관계를 연결어미로 잇는다. 주제 문장 하나는 짧아도
  된다.
- 문두 접속사를 금지하지 말 것. 구어 어미(`~거든요`)와 같은 접속사의 반복만 피한다.
  "그래서, 하지만, 다만, 따라서, 그런데"는 문장 관계를 밝히는 정상적인 수단이다.
- 의문형 제목은 장르로 판단할 것. 참조 문서(README, 설계서, 보고서)는 명사구,
  이야기체(블로그, 회고)는 의문형도 허용한다.
- 규칙을 검증할 때는 문장 단위 결함 목록(번역투, 피동, 사물 주어)만 보지 말고 문장
  길이 분포와 접속사 빈도를 같이 잴 것. 이번에 문장 단위 결함은 0건이었지만 문장
  길이가 전문 글의 절반이었다.
