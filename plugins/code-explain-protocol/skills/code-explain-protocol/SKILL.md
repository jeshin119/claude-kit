# Code Explain Protocol

## 사용 시점

- 사용한다: "이 코드 설명해줘", "이 프로젝트 구조 알려줘", "이거 왜 이렇게 동작해?",
  "이해가 안 돼"처럼 설명이나 이해를 명시적으로 요청하는 경우
- 사용하지 않는다: 기능 추가, 버그 수정, 리팩토링, 테스트 작성 등 구현 요청. 이런
  요청에는 평소대로 바로 작업한다

## 원칙

- 코드를 한 줄씩 순서대로 읽어주지 않는다. 구조를 먼저 보여주고 세부 코드는 마지막에
  보여준다
- 설명한 것과 이해시킨 것은 다르다. 설명한 뒤에는 반드시 확인 단계를 거친다
- 목적은 AI가 만든 코드를 감시하는 것이 아니다. 사용자가 이 시스템에 대해 스스로
  다음 질문이나 다음 변경을 떠올릴 수 있는 상태를 만드는 것이다

## 진행 순서

### 1단계: 구조 설명

다음 순서로만 설명하고 순서를 건너뛰지 않는다.

1. 전체 프로젝트나 시스템의 구조 (예: Client → API → Service → Repository → DB)
2. 각 컴포넌트의 역할을 한 줄로 요약
3. 컴포넌트 사이의 관계와 데이터 흐름 (요청이 들어와서 응답이 나가기까지)
4. 마지막에 실제 코드의 세부 사항

설명하는 과정에서 중복 설정, 이상한 로직, 불일치를 발견하면 반드시 짚어 준다.

### 2단계: 퀴즈

설명이 끝나면 바로 다음을 진행한다.

- 단순 암기형 질문이 아니라 데이터 흐름, 컴포넌트의 책임, 변경 영향 범위를 묻는
  질문을 2~4개 낸다
  - 예: "이 요청이 Router에서 Service로 넘어간 다음, 어떤 데이터를 들고 DB에
    접근하나요?"
  - 예: "이 함수를 수정하면 어떤 다른 부분이 영향을 받을까요?"
- 사용자가 답하면 맞았는지 짚어 주고, 틀리거나 애매한 부분은 그 부분만 다시 짧게
  설명한다

### 3단계: 미니 실험 (필요할 때만)

2단계에서도 이해되지 않는 부분이 있으면 다음을 한다.

- 실제 서비스 코드는 수정하지 않고, 해당 개념이나 흐름만 보여주는 작은 인터랙티브
  예시(HTML 등)를 만들어 제안한다
- 제품 코드가 아니라 이해를 위한 코드임을 명시한다

### 4단계: 정리

마지막에 사용자가 직접 한두 문장으로 구조를 요약해 보게 유도하거나, Claude가 핵심
모델을 한 문단으로 요약한다.

## 하지 말아야 할 것

- 구현이나 버그 수정 요청에 이 프로토콜을 강제로 적용하지 않는다
- "테스트를 통과했으니 이해한 것"으로 넘어가지 않는다
- 세부 코드부터 먼저 보여주지 않는다
