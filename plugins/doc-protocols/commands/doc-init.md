`project-doc-framework` 스킬을 불러 그 절차를 따른다. 대상 디렉터리는
`$1`이고, 비어 있으면 `docs`다.

## 순서

1. **먼저 저장소를 읽는다.** 파일 수, 언어, 커밋 이력, README 유무를 본다.
   사용자에게 규모를 묻기 전에 스스로 판단할 근거를 모은다.

2. **프로파일을 판정하고 근거를 한 줄로 말한다.** 예: "파일 3개에 단발 스크립트라
   S로 본다." 판정이 애매하면 그때만 `AskUserQuestion`으로 S/M/L을 묻는다.

3. **이미 있는 문서를 확인한다.** 대상 디렉터리에 파일이 있으면 **덮어쓰지 않는다.**
   무엇이 있는지 보고하고, 승급(파일 추가)인지 신규 생성인지 판정한 뒤 진행한다.

4. **템플릿을 복사한다.** 스킬 디렉터리의 `templates/`에서 해당 프로파일 파일만
   가져온다. 프로파일에 없는 파일은 만들지 않는다.

   | 프로파일 | 만드는 것 |
   |---|---|
   | S | `charter.md`, `journal.md` |
   | M | + `design.md`, `decisions/` |
   | L | + `report.md` |

   템플릿 안의 `M` `L` 표시 절 중 현재 프로파일보다 위인 것은 **지운다.**
   빈 절을 남기지 않는다.

5. **두 가지만 질문한다.** `1 문제와 배경`과 `6 성공 기준`은 사용자에게 물어야
   안다. 나머지는 `<!-- TODO -->`로 두고 진행 중에 채운다.

   성공 기준은 반드시 **숫자와 판정 방법**이 있어야 한다. 사용자가 "빨라지면
   좋겠다"처럼 답하면 현재값을 측정해서 목표 숫자를 제안하고 확인받는다.

   **`5 용어`는 `TODO`를 남기지 않는다.** 지금 확정된 것만 적고, 이름이 아직 없는
   용어는 이름 칸이 없는 표에 둔다.

6. **`2 해결 방법`을 쓸지 판정하고, 쓰기로 했으면 채운다.** 판정 질문은 하나다 —
   해결 방법을 이 프로젝트가 정하는가, 밖에서 받는가.

   | 이 프로젝트가 | 판정 |
   |---|---|
   | 해결 방법 자체를 내놓고 검증한다 (연구, 재현, PoC, 성능 개선) | 쓴다 |
   | 해결 방법이 밖에서 주어졌고 그걸 구현한다 (외주, 명세 구현, 이관) | 절을 지운다 |

   저장소만 보고 판단이 안 서면 그때만 `AskUserQuestion`으로 묻는다.

   쓰기로 했으면 1에서 규정한 문제의 어느 고리를 어디서 끊는지 쓰고, 각 단계를
   `7 기능 요구사항`의 `FR-nn`과 잇는다. 여기가 비면 문서가 문제 제기에서 끝나고,
   요약본이 원본보다 잘 읽히게 된다.

   지우기로 했으면 `1 문제와 배경` 끝에 명세의 출처를 한 줄 남기고, **지웠다는 사실과
   그 근거를 보고에 적는다.**

7. **`<프로젝트 이름>`, 날짜, 프로파일 표시를 실제 값으로 채운다.**

8. **목차를 생성한다.**

   ```bash
   python3 <스킬 디렉터리>/scripts/gen-toc.py <대상 디렉터리>/*.md
   ```

   템플릿의 `<!-- TOC -->` 자리에 h2/h3 목차가 들어간다. 손으로 쓰지 않는다.

9. **검증한다.**

   ```bash
   bash <스킬 디렉터리>/scripts/check-trace.sh <대상 디렉터리>
   ```

   갓 만든 문서는 사슬이 끊겨 있는 게 정상이다. 출력을 그대로 보여주고
   "이 항목들이 진행하면서 채워질 자리"라고 설명한다.

## 보고

2. 만든 파일 목록. 만들지 않은 파일과 그 이유
3. 사용자가 답한 `1`, `6` 요약. `2` 해결 방법은 채웠으면 요약을, 지웠으면 그 근거를
4. `check-trace.sh` 출력
5. 승급 조건 — 언제 M으로, 언제 L로 올려야 하는지 한 줄씩
