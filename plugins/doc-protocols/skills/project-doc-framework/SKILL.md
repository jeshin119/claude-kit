# Project Doc Framework

## 언제 이 스킬을 쓰는가

세 가지 국면 전부다.

| 국면 | 요청 예시 | 하는 일 |
|---|---|---|
| **세우기** | "문서 골격 잡아줘", "요구사항 정의서 만들어줘" | 규모를 판정하고 프로파일에 맞는 파일을 생성한다 |
| **갱신** | "지금까지 한 거 남겨줘", "이 결정 기록해줘" | 해당 층의 파일만 고친다. 다른 층은 건드리지 않는다 |
| **정리** | "다듬어줘", "설명체 줄여줘", "중복 빼줘", "목차 넣어줘" | `references/writing-rules.md`를 적용한다 |

트리거 아님

- 코드 주석, 커밋 메시지, PR 설명 → 평소대로 작업
- 에세이·블로그·회고 등 산문 윤문 → `humanize-korean`
- 코드·시스템의 동작 설명 → `code-explain-protocol`

## 원칙

**갱신 주기가 다른 내용을 같은 파일에 두지 않는다.** 한 번 정하고 안 바뀌는
것, 계속 덮어써야 하는 것, 지우면 안 되고 쌓기만 하는 것이 섞이면 문서가
썩는다. 층이 곧 파일 경계다.

**설명보다 요구사항을 우선한다.** 좋은 문장보다 **테스트할 수 있는 문장**을
우선한다. 문체 규칙 전문은 `references/writing-rules.md`에 있다.

**문서는 독자를 향한다.** 층 이름과 갱신 규칙은 문서를 쓰는 쪽의 사정이므로 본문에
쓰지 않는다. 파일 상단에는 그 자리에 "이 문서에 무엇이 있고 여기 없는 것은 어디에
있는지"를 적는다. `1 문제와 배경`은 해당 분야를 모르는 사람이 읽고 따라올 수 있어야
하고, 용어는 처음 나오는 자리에서 푼다. `journal/` 의 월별 보관분을 뺀 모든 파일
상단에 목차를 둔다.

## 1. 19항목 6층

| 층 | 갱신 방식 | 항목 | 파일 |
|---|---|---|---|
| **정의** | 초기 확정. 바꾸면 프로젝트 정체성이 바뀐다 | 1 문제와 배경 · 2 해결 방법 · 3 범위와 비범위 · 4 사용자와 이해관계자 · 5 용어 · 6 성공 기준 | `charter.md` |
| **계약** | 합의 대상. 변경하려면 협의한다 | 7 기능 요구사항 · 8 제약과 비기능 요구사항 · 9 인터페이스와 데이터 계약 | `charter.md` |
| **결정** | append only. 지우지 않는다 | 10 결정 기록 | `decisions/NNNN-*.md` |
| **현행** | 항상 최신으로 덮어쓴다 | 11 아키텍처 · 12 구현 현황 · 13 운영과 관측 | `design.md` |
| **기록** | 시간순으로 쌓기만 한다 | 14 작업 로그 · 15 검증 기록 · 16 변경 이력 | `journal.md` + `journal/YYYY-MM.md` |
| **종결** | 종료 시점 1회. 회차마다 갱신한다 | 17 결과와 한계 · 18 미결과 다음 단계 · 19 참고 자료 | `report.md` |

각 항목에 무엇을 쓰고 무엇을 쓰지 않는지는 `references/item-catalog.md`를 본다.

**번호는 고정이다.** 프로파일이 올라가도 기존 번호는 그대로고 항목만 늘어난다.
승급이 이어쓰기가 되고, 다시 쓰기가 되지 않는다.

**항목 집합은 프로젝트가 늘리지 않는다.** 쓸 자리가 없어 보이면 기존 항목 안에 h3로
넣는다. 프로젝트 문서에 새 최상위 번호를 만들면 그 번호가 다른 항목과 겹치고, 다른
파일의 참조가 조용히 다른 곳을 가리키게 된다. 항목 자체가 부족하다고 판단되면 이
프레임워크를 고치고, 그때 모든 참조를 함께 옮긴다.

## 2. 규모 프로파일

작업을 시작하기 전에 규모부터 판정한다. 판정 근거를 한 줄로 말하고 시작한다.

| 프로파일 | 대상 | 파일 | 항목 |
|---|---|---|---|
| **S** | 반나절~하루. 스크립트, 설정 변경, 단발 수정 | `charter.md`, `journal.md` | 1, 6, 7 / 14, 15 |
| **M** | 며칠~몇 주. 기능 하나, 도구 하나 | + `design.md`, `decisions/` | + 2, 3, 8 / 11, 12, 13 / 10 |
| **L** | 몇 달. 남이 인수받는다 | + `report.md` | 19개 전부 |

S는 5항목, M은 12항목, L은 19항목이다.

**승급 신호** — 하나라도 걸리면 다음 단계로 올린다.

- S → M: 결정을 뒤집은 적이 있다 / 파일이 5개를 넘는다 / 이틀 이상 걸렸다
- M → L: 나 말고 다른 사람이 손댄다 / 배포 대상이 있다 / 한 달을 넘겼다

승급할 때는 새 파일을 만들고 해당 항목만 추가한다. 기존 파일을 다시 쓰지 않는다.

파일 수와 경과일은 `scripts/check-trace.sh`가 대신 잰다. 나머지는 사람이 본다.

## 3. 추적 사슬

빈 목차 19개를 주면 안 채워진다. 항목을 잇는 사슬 두 개가 프레임워크를 작동시킨다.

**사슬 A — 목적이 소망이 아님을 증명한다**

```
6 성공 기준 (SC-nn)  →  15 검증 기록  →  17 결과와 한계
```

성공 기준 한 줄마다 실측값이 있고 달성/미달 판정이 있어야 한다. 어느 칸이 비면
그건 목적이 아니라 소망이다.

**사슬 B — 구현과 스코프를 맞춘다**

```
7 기능 요구사항 (FR-nn)  →  12 구현 현황  →  15 검증 기록
```

참조가 없는 요구사항은 미구현이다. 참조하는 요구사항이 없는 구현은 스코프
밖이다. 둘 다 보고에 올린다.

**ID 규칙**

| 접두사 | 대상 | 예 |
|---|---|---|
| `SC-nn` | 성공 기준 | `SC-01` |
| `FR-nn` | 기능 요구사항 | `FR-03` |
| `NFR-nn` | 제약·비기능 요구사항 | `NFR-02` |
| `ADR-nnnn` | 결정 기록 | `ADR-0007` |

ID는 재사용하지 않는다. 항목을 지워도 번호는 비워둔다.

## 4. 절차

### 세우기

1. 규모를 판정하고 근거를 말한다
2. `templates/`에서 해당 프로파일의 파일을 복사한다
3. 사용자에게 물어야 아는 것(1 문제와 배경, 6 성공 기준)만 질문한다. 나머지는
   `<!-- TODO -->`로 두고 진행 중에 채운다. **5 용어는 예외다.** 지금 확정된 것만
   적고 빈 칸을 `TODO`로 채우지 않는다. 이름이 아직 없는 용어는 이름 칸이 없는 표에
   둔다
4. 2 해결 방법을 채운다. 1에서 규정한 문제의 어느 고리를 어디서 끊는지 쓰고, 각
   단계를 7의 `FR-nn`과 잇는다. 여기가 비면 문서가 문제 제기에서 끝난다.
   **단, 해결 방법이 밖에서 주어진 프로젝트(외주, 명세 구현, 이관)는 이 절을 만들지
   않는다.** 대신 1 끝에 명세의 출처를 한 줄 남기고, 생략한 사실과 이유를 보고에
   적는다. 판정 기준은 `references/item-catalog.md`의 2번 항목에 있다
5. 성공 기준에 SC ID와 **숫자**를 붙인다. 숫자가 없으면 사슬 A가 끊어진다
6. `scripts/gen-toc.py`로 목차를 채운다. 템플릿의 `<!-- TOC -->` 자리에 들어간다

### 갱신

1. 요청 내용이 어느 층인지 먼저 판정한다
2. **그 층의 파일만** 연다. 결정층은 새 파일을 추가하고 기존 파일을 고치지 않는다
3. 현행층(`design.md`)은 덮어쓰고, 기록층(`journal.md`)은 아래에 붙인다
   - 작업 로그(14)는 **날짜 단위**로 묶는다. 같은 날 세션이 여러 개면 그 날짜 절에
     이어 붙이고 절을 새로 만들지 않는다
   - 달이 바뀌면 **14와 15를** `journal/YYYY-MM.md`로 옮기고 `journal.md`에는 링크만
     남긴다. 14는 통째로 옮기고, 15는 각 ID의 **가장 최근 한 줄만 남기고** 옮긴다.
     17 판정이 최신 실측값을 바로 봐야 하기 때문이다
   - 16은 옮기지 않는다. 계약이 바뀐 횟수만큼만 늘어난다
4. 요구사항이나 성공 기준이 바뀌면 계약층을 고치고, 왜 바꿨는지를 결정층에 남긴다
5. 절을 추가·삭제·개명했으면 `scripts/gen-toc.py`를 다시 돌린다

### 정리

`references/writing-rules.md`의 절차를 따른다. 요약하면 문체 → 제거 → 구조 순서고,
편집 전에 원본을 스크래치패드에 백업하고, 끝나면 검증 grep을 돌린다.

## 5. 검증

문서를 손댄 뒤 반드시 돌린다.

```bash
# 추적 사슬 — 끊긴 ID 확인. 스킬 디렉터리 기준 경로다
bash <스킬 디렉터리>/scripts/check-trace.sh docs/

# 프레임워크 용어가 본문에 남았는지
grep -rnE '정의층|계약층|결정층|현행층|기록층|종결층' docs/

# 목차 — 마커가 없는 파일과 갱신
grep -rL '<!-- TOC -->' docs/ --include='*.md' --exclude-dir=journal
python3 <스킬 디렉터리>/scripts/gen-toc.py docs/*.md docs/decisions/*.md
```

`check-trace.sh`는 두 가지를 본다. 하나는 추적 사슬이다. charter 표의 첫 열에서
SC/FR ID를 뽑아 journal·design·report에서 참조를 찾고, 끊긴 쪽을 출력한다.

다른 하나는 **프로파일 승급 신호**다. 현재 프로파일을 파일 존재로 판정하고
(design.md 없으면 S, report.md 없으면 M), 기계로 잴 수 있는 신호 셋 — 추적 파일 수,
경과일, `decisions/` 존재 — 을 검사한다. 승급 조건이 걸리면 승급하거나, 승급하지
않는 이유를 보고 2번에 적는다. 나머지 신호(결정을 뒤집었나 / 남이 손대나 / 배포
대상이 있나)는 스크립트가 못 재니 갱신할 때 직접 본다.

없는 파일은 건너뛰므로 프로파일 S에서도 그대로 돌아간다. git 저장소가 아니거나
날짜를 못 찾으면 그 검사만 건너뛰고 거짓 신호를 만들지 않는다. 종료 코드가 0이
아니면 출력을 보고에 그대로 싣는다.

## 6. 사실 관계 취급

- **고친다**: 문서 내부 모순 — 헤더의 건수와 표의 행 수 불일치, 잘못된 항목 번호
  참조, 날짜 오기. 무엇을 고쳤는지 보고에 남긴다
- **고치지 않는다**: 실행 환경·아키텍처·채택 결정 등 실질 내용. 문서와 실제가
  다르면 **본문은 그대로 두고 별도로 질문한다**

## 7. 보고 형식

작업 후 아래를 제시한다.

1. 프로파일 판정과 근거 (세우기·승급일 때)
2. 손댄 층과 파일. 손대지 않은 층
3. 변경 요약 — 전/후 대비 표
4. 제거한 항목 — 항목별 사유 표
5. **제거 검토했으나 남긴 항목 — 남긴 사유**
6. 끊긴 추적 사슬 — 검증 없는 SC, 구현 없는 FR, 요구사항 없는 구현
7. 문서 내부 오류 수정 내역
8. 확인이 필요한 실질 불일치 (있으면)
