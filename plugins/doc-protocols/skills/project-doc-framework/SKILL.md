# Project Doc Framework

이 파일이 절차의 원본이다. `/doc-init` 과 `/doc-log` 는 이 파일의 **세우기**와
**갱신** 절차를 그대로 부른다. 절차를 고칠 때는 여기만 고친다.

## 언제 쓰는가

| 국면 | 요청 예시 | 하는 일 |
|---|---|---|
| **세우기** | "문서 골격 잡아줘", "요구사항 정의서 만들어줘" | 규모를 판정하고 프로파일에 맞는 파일을 만든다 |
| **갱신** | "지금까지 한 거 남겨줘", "이 결정 기록해줘" | 해당 층의 파일만 고친다 |
| **정리** | "다듬어줘", "설명체 줄여줘", "중복 빼줘", "목차 넣어줘" | `references/writing-rules.md` 를 적용한다 |

트리거 아님

- 코드 주석, 커밋 메시지, PR 설명 → 평소대로 작업
- 에세이·블로그·회고 등 산문 윤문 → `humanize-korean`
- 코드·시스템의 동작 설명 → `code-explain-protocol`

## 원칙

**문서는 다음 세션의 입력이다.** 대화에만 있는 맥락은 세션이 끝나면 사라진다.
특히 어떤 접근을 왜 버렸는지가 먼저 사라지고, 다음 세션이 그 접근을 다시 꺼낸다.
기록층과 결정층은 사람이 나중에 읽을 자료이기 전에, 다음 세션이 읽고 시작하는
자리다.

**검증이 병목이다.** 코드를 쓰는 속도가 아니라 그 코드가 맞다고 확인하는 속도가
프로젝트의 상한이다. 그래서 무엇을 만들었는지보다 **무엇을 무엇으로 확인했는지**를
남긴다. 15 검증 기록의 `방법` 칸이 그 강도를 적는 자리다.

**갱신 주기가 다른 내용을 같은 파일에 두지 않는다.** 한 번 정하고 안 바뀌는 것,
계속 덮어써야 하는 것, 지우면 안 되고 쌓기만 하는 것이 한 파일에 섞이면 갱신할
때마다 문단별로 어느 쪽인지 판단해야 하고, 그 비용 때문에 갱신이 멈춘다. 층이 곧
파일 경계다.

**독자를 기준으로 쓴다.** 좋은 문장보다 검증할 수 있는 문장을 우선한다. 층 이름과
갱신 규칙은 문서를 쓰는 쪽의 사정이므로 본문에 쓰지 않는다. 파일 상단에는 이
문서에 무엇이 있고 여기 없는 것은 어디에 있는지를 한 문단으로 적는다. `1 문제와
배경`은 그 분야를 모르는 사람이 읽고 따라올 수 있어야 하고, 용어는 처음 나오는
자리에서 푼다. `journal/` 의 월별 보관분을 뺀 모든 파일 상단에 목차를 둔다. 문체
규칙 전문은 `references/writing-rules.md` 에 있다.

## 19항목 6층

| 층 | 갱신 방식 | 항목 | 파일 |
|---|---|---|---|
| **정의** | 초기 확정. 바꾸면 프로젝트 정체성이 바뀐다 | 1 문제와 배경 · 2 해결 방법 · 3 범위와 비범위 · 4 사용자와 이해관계자 · 5 용어 · 6 성공 기준 | `charter.md` |
| **계약** | 합의 대상. 바꾸려면 협의한다 | 7 기능 요구사항 · 8 제약과 비기능 요구사항 · 9 인터페이스와 데이터 계약 | `charter.md` |
| **결정** | 추가만 한다. 지우지 않는다 | 10 결정 기록 | `decisions/NNNN-*.md` |
| **현행** | 항상 최신으로 덮어쓴다 | 11 아키텍처 · 12 구현 현황 · 13 운영과 관측 | `design.md` |
| **기록** | 시간순으로 쌓기만 한다 | 14 작업 로그 · 15 검증 기록 · 16 변경 이력 | `journal.md` + `journal/YYYY-MM.md` |
| **종결** | 상태가 종료·보류로 바뀔 때 | 17 결과와 한계 · 18 미결과 다음 단계 · 19 참고 자료 | `report.md` |

각 항목에 무엇을 쓰고 무엇을 쓰지 않는지는 `references/item-catalog.md` 에 있다.

**번호는 고정이다.** 프로파일이 올라가도 기존 번호는 그대로고 항목만 늘어난다.
**항목 집합은 프로젝트가 늘리지 않는다.** 쓸 자리가 없어 보이면 기존 항목 안에
h3(셋째 단계 제목)로 넣는다. 새 최상위 번호를 만들면 다른 항목과 겹치고, 다른
파일의 참조가 눈에 띄지 않게 다른 곳을 가리킨다.

## 규모 프로파일

작업을 시작하기 전에 규모부터 판정하고 근거를 한 줄로 말한다.

| 프로파일 | 대상 | 진행 중에 두는 파일 | 항목 |
|---|---|---|---|
| **M** | 며칠~몇 주. 기능 하나, 도구 하나 | `charter.md`, `journal.md`, `design.md`, `decisions/` | 1, 2, 3, 6, 7, 8 / 10 / 11, 12, 13 / 14, 15, 16 (13개) |
| **L** | 몇 달. 남이 읽거나 손댄다 | + `report.md` | + 4, 5, 9, 19 (19개) |

M 아래는 없다. 하루짜리 작업이라도 문제와 성공 기준을 안 적으면 남는 것이 없다.

**종결층은 프로파일이 아니라 상태가 연다.** 상태가 진행에서 종료나 보류로 바뀌면
M 도 `report.md` 를 만들고 17·18 을 쓴다. 19 참고 자료만 L 전용이다.

**승급 신호** — 하나라도 걸리면 M 에서 L 로 올린다. 나 말고 다른 사람이 손댄다 /
배포 대상이 있다 / 한 달을 넘겼다. 승급은 파일과 항목을 **추가**하는 것이고 기존
파일을 다시 쓰지 않는다. 경과일은 `scripts/check-trace.sh` 로 확인하고 나머지
신호는 사람이 본다.

## 추적 사슬과 ID

빈 목차 19개를 주면 채워지지 않는다. 항목끼리 서로를 참조시켜 빈칸이 드러나게 하는
장치가 사슬이다.

```
사슬 A   6 성공 기준 (SC-nn)      →  15 검증 기록  →  17 결과와 한계
사슬 B   7 기능 요구사항 (FR-nn)  →  12 구현 현황  →  15 검증 기록
```

사슬 A: 성공 기준마다 실측값과 달성·미달 판정이 있어야 한다. 한 칸이라도 비면
목적이 아니라 바람이다. 사슬 B: 구현 기록이 없는 요구사항은 미구현이고, 대응하는
요구사항이 없는 구현은 범위 밖이다. 둘 다 보고에 올린다.

| 접두사 | 원어 | 대상 | 예 |
|---|---|---|---|
| `SC-nn` | Success Criterion | 성공 기준 | `SC-01` |
| `FR-nn` | Functional Requirement | 기능 요구사항 | `FR-03` |
| `NFR-nn` | Non-Functional Requirement | 제약·비기능 요구사항 | `NFR-02` |
| `ADR-nnnn` | Architecture Decision Record | 결정 기록 | `ADR-0007` |

ID 는 재사용하지 않는다. 항목을 지워도 번호는 비워 둔다.

## 절차

### 세우기

대상 디렉터리는 명령 인자로 받고, 없으면 `docs` 다.

1. **저장소를 먼저 읽는다.** 파일 수, 언어, 커밋 이력, README 유무를 본다. 규모를
   묻기 전에 스스로 판단할 근거를 모은다
2. **프로파일을 판정하고 근거를 한 줄로 말한다.** 예: "기능 하나짜리에 배포 대상이
   없어 M 으로 본다." 애매할 때만 `AskUserQuestion` 으로 M/L 을 묻는다
3. **이미 있는 문서를 확인한다.** 대상 디렉터리에 파일이 있으면 덮어쓰지 않는다.
   무엇이 있는지 보고하고, 승급(파일 추가)인지 신규 생성인지 판정한 뒤 진행한다
4. **`templates/` 에서 프로파일에 맞는 파일만 복사한다.** M 은 `charter.md`
   `journal.md` `design.md` `decisions/`, L 은 거기에 `report.md`. M 에서는
   템플릿의 `L` 표시 절을 지우고 빈 절을 남기지 않는다
5. **두 가지만 질문한다.** 1 문제와 배경, 6 성공 기준은 사용자에게 물어야 안다.
   나머지는 `<!-- TODO -->` 로 두고 진행 중에 채운다. 성공 기준에는 `SC-nn` 과
   **숫자, 판정 방법**을 붙인다. 사용자가 "빨라지면 좋겠다" 처럼 답하면 현재값을
   재서 목표 숫자를 제안하고 확인받는다. 잴 대상이 아직 없으면 현재값을 `미측정`
   으로 적고 목표값과 판정 방법은 채운다. 지어낸 숫자를 넣지 않는다.
   **5 용어는 `TODO` 를 남기지 않는다.** 확정된 것만 적고, 이름이 아직 없는 용어는
   이름 칸이 없는 표에 둔다
6. **2 해결 방법을 쓸지 판정한다.** 질문은 하나다 — 해결 방법을 이 프로젝트가
   정하는가, 밖에서 받는가. 스스로 내놓고 검증하면(연구, 재현, PoC, 성능 개선)
   쓴다. 밖에서 받아 구현하면(외주, 명세 구현, 이관) 절을 지우고 1 끝에 명세의
   출처를 한 줄 남긴다. 저장소만 보고 판단이 안 서면 그때만 묻는다. 쓰기로 했으면
   문제가 생기는 과정의 어느 단계에서 어떻게 개입하는지 쓰고, 각 단계를 7 의
   `FR-nn` 과 잇는다. 지웠으면 그 사실과 근거를 보고에 적는다
7. **7 기능 요구사항을 `FR-nn` 으로 채운다.** 2 의 각 단계가 어느 요구사항으로
   이어지는지 맞춘다. 여기가 비면 사슬 B 가 처음부터 끊긴 채로 시작한다
8. **되돌리기 어려운 결정을 적는다.** 요구사항 다음이고 코드를 쓰기 전이다. 아래
   다섯 축을 하나씩 물어 해당하는 것을 전부 고르고 `decisions/` 에 파일을 하나씩
   만든다. **개수 목표는 없다.** 해당 없는 축은 그렇게 보고한다. 되돌리기 쉬운
   결정(이름, 패키지 구조, 로깅 포맷)은 적지 않는다.

   | 축 | 묻는 것 |
   |---|---|
   | 도메인 경계 | 무엇과 무엇을 어디서 자르는가 |
   | 데이터 모델과 식별자 | 무엇을 키로 삼고 어떤 형태로 저장하는가 |
   | 일관성 모델 | 언제 상태를 바꾸고, 실패하면 무엇을 되돌리는가 |
   | 인증·인가 | 누가 무엇을 할 수 있는가 |
   | 외부 시스템과의 계약 | 무엇에 의존하고 그 계약이 바뀌면 어떻게 되는가 |

   지금 답이 나오면 `상태: 유효` 로 채운다. 안 나오면 `상태: 미결` 로 두고 "정해질
   때까지 미루는 것" 만 채운 뒤 **그 영역을 건드리는 작업을 뒤로 미룬다.** 미결
   목록은 보고에 반드시 싣는다
9. **`design.md` 12 의 착수 순서를 채운다.** FR 을 어떤 순서로 할지와 각각을
   무엇으로 확인할지를 같이 적는다. 순서는 걸리는 시간이 아니라 끝났을 때 맞는지
   짧게 확인할 수 있는가로 정한다. 확인 수단이 없으면 그 수단을 먼저 만드는 작업으로
   쪼갠다. 첫 항목은 기능 하나를 입구부터 저장소까지 관통시키는 것으로 둔다
10. **템플릿 잔재를 지운다.** `<프로젝트 이름>`, 날짜, 프로파일을 실제 값으로
    채운다. 헤더의 프로파일 칸은 `M` 이나 `L` 한 글자만 남긴다. `생성 시 지침`
    주석, `예시:` 주석, 제목의 `L` 표시, 안 채운 `YYYY-MM-DD` 를 남기지 않는다.
    `journal.md` 는 이 단계에서만 손댄다. 제목을 채우고 14 의 빈 날짜 절을 지운다.
    첫 날짜 절은 갱신 절차가 만든다

    ```bash
    grep -rn '<프로젝트 이름>\|생성 시 지침\|예시:\|path/to/file' <대상 디렉터리>/
    grep -rnE '^#{2,3} .*`L`' <대상 디렉터리>/
    ```
11. **프로젝트 `CLAUDE.md` 가 없을 때만 갱신 규칙 네 줄을 넣어 만든다.** 스킬은
    불릴 때만 로드되므로, 작업 중에 결정과 측정값이 어디로 가는지는 항상 로드되는
    규칙 파일에 적어 두어야 한다. **이미 있으면 손대지 않고** 네 줄을 보고에 실어
    사용자가 정하게 한다. 그 파일은 저장소의 모든 세션에 로드되고 커밋되므로, 사용자가
    일부러 다르게 써 둔 절과 이전 판을 구분하지 못한 채 병합하면 모순된 지시가
    남는다. 전역 `~/.claude/CLAUDE.md` 는 어느 경우에도 건드리지 않는다. `<문서
    디렉터리>` 는 이번에 실제로 쓴 경로로 바꿔 적는다.

    ```markdown
    ## 문서
    - 결정을 새로 정하거나 뒤집으면 `<문서 디렉터리>/decisions/` 에 파일을 추가한다
    - 측정값이 나오면 `<문서 디렉터리>/journal.md` 15 에 방법·명령어·값을 적는다
    - 요구사항·성공 기준이 바뀌면 `<문서 디렉터리>/charter.md` 를 고치고 16 에 남긴다
    - 세션을 끝낼 때 `/doc-log <문서 디렉터리>` 를 돌린다
    ```
12. **목차를 만든다.** `scripts/gen-toc.py` 가 템플릿의 `<!-- TOC -->` 자리에
    채운다. 손으로 쓰지 않는다
13. **`scripts/check-trace.sh` 로 검증한다.** 갓 만든 문서는 12 와 15 가 비어
    있어 종료 코드 1 이 정상이다. 출력을 그대로 보여주고 앞으로 채울 자리라고
    설명한다. 9 면 경로나 `charter.md` 가 없는 것이니 고친다

**보고**: 프로파일 판정과 근거 / 만든 파일과 만들지 않은 파일 / 사용자가 답한 1·6
요약과 2 의 처리 / 되돌리기 어려운 결정 목록(정한 것과 미결, 미결마다 미루는 작업 한
줄) / `CLAUDE.md` 처리 / `check-trace.sh` 출력과 종료 코드 / 언제 L 로 올려야 하는지
한 줄.

### 갱신

대상 디렉터리에 `journal.md` 가 없으면 멈추고 세우기를 먼저 하라고 알린다.

1. **실제로 무엇이 바뀌었는지 확인한다.** 대화 기억이 아니라 파일 변경을 근거로
   삼는다.

   ```bash
   git status --short && git log --oneline -20 && git diff --stat
   ```
2. **요청이 어느 층인지 판정하고 그 층의 파일만 연다.** 결정층은 새 파일을 추가하고
   기존 파일을 고치지 않는다. 현행층(`design.md`)은 덮어쓰고, 기록층(`journal.md`)은
   아래에 붙인다
3. **14 작업 로그에 붙인다.** 오늘 날짜 절이 있으면 그 절에 이어 붙이고 새 절을
   만들지 않는다. 한 일은 결과만 적는다. 막힌 것은 증상·원인·해결로 적고, 원인 칸이
   비면 아직 안 풀린 것이니 그렇게 적는다. **방향을 한 번이라도 바꿨으면 버린 접근과
   버린 이유를 적는다.** 버린 이유가 설계 판단이면 14 가 아니라 `decisions/` 에 ADR
   로 남기고 여기서는 링크만 둔다
4. **15 검증 기록에 붙인다.** 이번 세션에서 명령어를 돌려 값을 얻었으면 날짜, 대상
   ID, 방법, 명령어, 실측값을 적는다. 판정하지 않는다. "통과" 가 아니라 값을 적는다.
   `방법` 칸은 `타입·컴파일` / `테스트(스펙 확인)` / `테스트(미확인)` / `실행` /
   `정적분석` / `LLM 검토` 중 하나다. **이번 세션이 테스트를 쓰고 이번 세션이
   구현했으면 `테스트(미확인)` 이다.** 통과 여부가 아니라 사람이 스펙을 확인했는지가
   갈림길이다. 이번 세션이 스스로 코드를 훑어본 것은 적지 않는다. 측정한 게 없으면
   이 항목은 건드리지 않는다
5. **계약이 바뀌었으면 16 에 적는다.** 요구사항이나 성공 기준을 고쳤을 때만이다.
   절은 번호가 아니라 이름으로 적는다. `charter.md` 를 고치고 왜 바꿨는지를
   `decisions/` 에 남긴다
6. **월별 보관을 확인한다.** 14 에 지난 달 날짜 절이 있으면 `journal/YYYY-MM.md` 로
   옮기고 `journal.md` 상단 "지난 기록" 에 링크를 추가한다. 15 의 지난 달 행도 같은
   파일로 옮기되, **각 ID 의 가장 최근 한 줄은 `journal.md` 에 남긴다.** 17 판정이
   최신 실측값을 바로 봐야 하기 때문이다. 남긴 줄의 사본은 보관 파일에도 넣어 그
   달의 추이를 온전하게 한다. 옮긴 직후 15 의 행 수가 `charter.md` 의 SC + FR 개수를
   넘으면 같은 ID 가 두 줄 남은 것이니 오래된 쪽을 옮긴다. 16 은 옮기지 않는다
7. **다른 층이 낡았는지 점검한다.** 아키텍처나 구현이 바뀌었으면 `design.md` 를
   갱신해야 한다. 대신 고치지 말고 무엇이 낡았는지 보고한다. 결정을 뒤집었으면
   `decisions/` 에 새 파일이 필요하다고 알린다. `상태: 미결` 인 결정이 있고 이번
   세션이 그 영역을 건드렸으면 그 사실을 보고에 올린다
8. **일이 멈췄으면 종결 절차를 제안한다.** 사용자가 종료나 보류를 말했거나 마지막
   기록에서 시간이 크게 벌어졌으면 아래 종결·보류로 넘어가자고 제안한다. 사용자가
   진행 중이라고 하면 그대로 둔다
9. 절을 추가·삭제·개명했으면 `scripts/gen-toc.py` 를 다시 돌린다
10. **`scripts/check-trace.sh` 로 검증한다**

**보고**: 14 / 15 / 16 에 붙인 줄 수와 버린 접근 유무 / 월별 보관 여부 / 낡았을
가능성이 있는 다른 층과 미결 결정 / `check-trace.sh` 의 진척 세 줄과 이번에 달라진
부분 / 승급 신호나 종결 제안이 있으면 어떻게 할지, 안 한다면 그 이유.

### 종결·보류

프로파일과 무관하게 상태가 진행에서 종료나 보류로 바뀔 때 한다.

1. `charter.md` 헤더의 `상태` 를 바꾼다
2. `report.md` 가 없으면 템플릿에서 만든다. M 은 17 과 18 만 쓰고 19 는 지운다
3. 17 에 `SC-nn` 마다 목표값·실측값·판정을 채운다. 값은 전부 15 에 이미 있어야
   하고 여기서 새로 재지 않는다. 잴 수 없었으면 `해당 없음` 으로 확정하고 사유를
   적는다
4. 18 에 답을 못 찾은 질문과 다음 회차 후보를 적는다. **보류라면 무엇 때문에
   멈췄는지와 재개 조건이 본문이다**
5. `decisions/` 에 `상태: 미결` 로 남은 파일이 있으면 18 에 그대로 옮긴다. 재개할
   때 제일 먼저 막히는 지점이다
6. `scripts/gen-toc.py` 를 다시 돌린다

### 도식

11 아키텍처의 구성, 요청이 지나가는 순서, 상태 전이는 글로만 쓰면 읽는 쪽이
머릿속에서 다시 그려야 한다. 아래 셋 중 하나에 걸리면 `archify` 스킬로 그린다.

- 구성 요소가 넷을 넘고 그 사이 관계가 한 방향이 아니다
- 한 요청이 지나는 단계가 셋을 넘는다
- 상태가 셋을 넘고 전이에 조건이 붙는다

산출물은 `docs/diagrams/` 에 두고 11 에서 링크한다. 그림도 현행층이라 구조가
바뀌면 다시 그린다. **본문 설명을 그림으로 대체하지 않는다.** 그림은 grep 에 걸리지
않고 diff 로 읽히지 않아서, 그림만 남기면 다음 세션이 무엇이 바뀌었는지 알 수 없다.

### 정리

`references/writing-rules.md` 의 절차를 따른다. 문체 → 제거 → 구조 순서고, 편집
전에 원본을 스크래치패드에 백업하고, 끝나면 검증 grep 을 돌린다.

## 검증

문서를 손댄 뒤 반드시 돌린다.

```bash
# 추적 사슬 · 판정 근거 · ADR 참조 · 진척 · 승급 신호
bash <스킬 디렉터리>/scripts/check-trace.sh <대상 디렉터리>

# 프레임워크 용어가 본문에 남았는지
grep -rnE '정의층|계약층|결정층|현행층|기록층|종결층' <대상 디렉터리>/

# 템플릿 잔재
grep -rn '<프로젝트 이름>\|생성 시 지침\|예시:\|path/to/file' <대상 디렉터리>/
grep -rnE '^#{2,3} .*`L`' <대상 디렉터리>/

# 목차 — 마커가 없는 파일 확인과 갱신
grep -rL '<!-- TOC -->' <대상 디렉터리>/ --include='*.md' --exclude-dir=journal
find <대상 디렉터리> -name '*.md' -not -path '*/journal/*' \
  -exec python3 <스킬 디렉터리>/scripts/gen-toc.py {} +
```

`check-trace.sh` 가 확인하는 다섯 가지.

| 검사 | 무엇을 보는가 |
|---|---|
| 추적 사슬 | charter 표 첫 열의 SC/FR ID 를 `journal.md` 15, `design.md` 12, `report.md` 17 **절 안에서만** 찾는다. 실측값·판정·상태 칸이 비었거나 미확정인 행도 잡는다 |
| 판정 근거의 강도 | 17 에서 `달성` 인 `SC-nn` 이 15 에서 한 번도 `타입·컴파일`·`테스트(스펙 확인)`·`실행`·`정적분석` 으로 측정된 적이 없으면 잡는다. 15 에 `방법` 칸이 없으면 건너뛰고 그 사실만 알린다. 라벨은 자기 신고라 거짓 라벨은 못 잡는다 |
| ADR 참조 | 본문이 `ADR-0007` 을 참조하는데 `decisions/0007-*.md` 가 없으면 잡는다. 아무도 참조하지 않는 ADR 은 정상이다 |
| 진척 | 성공 기준과 요구사항이 몇 개 중 몇 개까지 왔는지, 미결 결정 건수, 마지막 작업 기록일. 세는 기준은 ID 가 있는지가 아니라 칸이 채워졌는지다 |
| 승급 신호 | 프로파일은 charter 헤더에서 읽고, 시작일은 헤더의 `시작` 행에서 읽되 없으면 git 첫 커밋을 쓴다. 경과일만 기계로 확인한다 |

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 끊긴 것도 승급 신호도 없다 | — |
| 1 | 사슬이 끊겼거나 ADR 참조가 깨졌다 | 채우거나, 지금 안 채우는 이유를 보고에 적는다 |
| 2 | 승급 조건에 걸렸다 | 승급하거나, 안 하는 이유를 보고에 적는다 |
| 3 | 둘 다 | 위 둘을 같이 한다 |
| 9 | 실행 오류 | 경로와 `charter.md` 존재를 확인한다 |

0 이 아니면 출력을 보고에 그대로 싣는다. 착수 직후의 1 은 정상이다. 없는 파일은
건너뛰므로 `report.md` 가 없는 진행 중 프로젝트에서도 돌아간다.

## 사실 관계 취급

- **고친다**: 문서 내부 모순 — 헤더의 건수와 표의 행 수 불일치, 잘못된 항목 번호
  참조, 날짜 오기. 무엇을 고쳤는지 보고에 남긴다
- **고치지 않는다**: 실행 환경·아키텍처·채택 결정 등 실질 내용. 문서와 실제가
  다르면 본문은 그대로 두고 별도로 질문한다

## 보고 형식

세우기와 갱신은 각 절차 끝의 **보고** 항목을 따른다. 그 밖의 작업은 아래를 제시한다.

1. 손댄 층과 파일. 손대지 않은 층
2. 변경 요약 — 전/후 대비 표
3. 제거한 항목과 **제거 검토했으나 남긴 항목** — 각각 사유
4. `check-trace.sh` 출력 — 종료 코드, 끊긴 사슬, 진척 세 줄, 미결 결정
5. 문서 내부 오류 수정 내역
6. 확인이 필요한 실질 불일치 (있으면)
